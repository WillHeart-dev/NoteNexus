01

缘起：复习时最难的不是学，是「整理」

这个项目不是先有技术再找场景，而是从三件很具体的麻烦事倒推出来的。

痛点 01

资料散在三四个地方

课件在群里、笔记在网盘、真题在聊天记录里。考前想问「上次那份讲到第几章」，得挨个翻，还常常翻到旧版本。

痛点 02

几百页，不知道看哪

期末范围就是整本 PPT。想快速过一遍重点，只能从头翻到尾，或者在群里问「有没有人整理过」——然后没人整理。

痛点 03

学得怎么样，全靠感觉

做过的题、错过的点没有记录。复习计划凭印象安排，容易一直重复已经会的，真正薄弱的地方反而没碰。

于是把目标拆成三件可落地的事

① 统一管理

以「小组」为唯一容器。资料、问答、讲义、习题、评论全部挂在组下，一组一群、群即边界，不再有「文件到底在哪」这个问题。

② 让资料能回答

入库后的资料可被检索。提问直接得到带出处的答案；资料里没有的就明确拒答，不编。

③ 把学习量化

做题正确率 → 知识点掌握度 → 图谱上的强弱分布 → 学习路径的先后顺序。复习从「凭感觉」变成「看数据」。

把散落的资料收进一个组，再把组里的资料变成能问答、能复习、能测、能定位薄弱点的学习资产。 —— 整个项目的设计主线，也是所有模块取舍的依据

这条主线决定了后面的技术选择：既然要「统一管理」，就必须有严格的组级数据隔离和一套可靠的文件入库流水线； 既然要「能回答」，就必须做检索增强而不是把全文塞给模型；既然要「量化」，就必须把题目、知识点、掌握度连成一条可计算的数据链。

02

系统全貌：一个后端，四套存储

前后端分离。后端按 Controller → Service → Mapper 分层，业务规则与权限判断全部收在 Service； 外部能力通过 engine 适配层接入，换存储不影响业务代码。

为什么不用一套库解决：MySQL 没有成熟的向量索引；全文索引对中文支持差；大文件塞进数据库会拖垮备份与迁移。四套存储各自最擅长的事，用 chunk_id 把三份副本对齐，重建时以 MySQL 为准。

03

模块功能：八个面向用户的能力

前端入口统一在 /app/*，每个模块对应后端一个包。下面按「解决什么问题 → 具体做了什么」来讲。

账号与权限 auth · user

登录一次，之后所有请求自动带身份；不同角色能看到的东西不同。

  • JWT 双令牌：access token 30 分钟放内存，refresh token 走 httpOnly cookie 14 天，刷新时轮换并作废旧令牌
  • 两级正交角色：系统级 ADMIN/USER 与组内 OWNER/MEMBER 互不推导，管理员默认进不了业务区
  • 密码 BCrypt 加盐哈希；改密后强制下线其他会话

学习小组 group

一组一群，群就是数据边界。所有资料、问答、习题都只在这个边界内可见。

  • 创建小组、邀请制加入（发邀请 → 受邀人接受）、申请制加入（申请 → 群主审批）
  • 群主可改名、移除成员、转让、解散；成员列表带角色标识
  • 删除是逻辑删除，历史问答与引用快照保留，避免「资料一删记录就碎」

资料中心 document · ingestion

上传、预览、下载、删除；上传后自动跑一遍解析入库，完成后才能被检索到。

  • 分片上传：初始化 → 并发传分片（MD5 校验）→ 合并；中断可续传，同组同文件可秒传
  • 支持 txt / md / pdf / docx，解析器工厂按扩展名分发，加格式只需实现一个接口
  • 状态机 UPLOADED → PROCESSING → READY / FAILED，失败可一键重试，错误原因落库

知识问答 qa

问一句，得到一段带出处的答案；资料里没有的，直接说没有。

  • 混合检索：向量通道 + 关键词通道并行，RRF 融合排序，再聚类与邻窗扩展补上下文
  • 四级证据等级（无 / 弱 / 部分 / 充分）随答案返回，让用户知道这句话有多硬
  • 引用可回溯：每条引用带文件名、切片序号、相关度，点开看原文；反馈（有用/没用）落库统计

复习讲义 review

一键把全组资料汇总成一份结构统一的 Markdown 讲义，考前直接看。

  • map / reduce 两阶段：先逐篇提炼要点，再合并成固定六章（导览 / 精讲 / 易混对比 / 例题 / 自测 / 速记卡）
  • 全程标注来源，reduce 阶段禁止引入原文没有的内容
  • 异步生成 + 前端轮询，关掉页面也能回来下载；产物直接存 MinIO 并可下载 .md

练习题库 exercise

从资料里自动出题，在线作答、即时判分，按知识点算正确率。

  • LLM 从切片中抽题：题干 / 选项 / 答案 / 解析 / 出处，每题带知识点标签
  • 作答写 exercise_attempts，同一题多次作答以最近一次为准
  • 统计按「用户 × 小组 × 知识点」聚合——这是后面掌握度计算的数据源

知识图谱与学习路径 graph

把资料里的知识点连成图，再按先后关系排出「先学什么」，并标出每个人的薄弱点。

  • LLM 抽知识点与关系（先修 / 组成 / 相关），每条关系附原文依据；同名概念归一合并
  • 拓扑分层生成学习路径；检测到环就断环，保证一定出得来；孤立点归入末尾阶段
  • 掌握度由做题正确率折算（≥85% 已掌握 / ≥60% 一般 / <60% 薄弱），阶段内薄弱优先

知识库评论 · 运营后台 discussion · metrics

评论区挂在学习资料模块底部，针对整个知识库发表看法；管理员另有一套用户管理与 ETL 运维视图。

  • 评论区是纯 CRUD，无 AI 参与——一库一评论区，引用回复让建议能落到具体评论
  • 后台可查用户列表与状态、ETL 成功/失败/积压统计，异常任务一眼能看到
  • 每次 LLM 调用记账：模块、端点、耗时、token、估算成本，便于排查「哪一步贵」
04

三条核心链路（技术部分）

上面八个能力里，真正吃技术的是三条链路：资料怎么进得来、问题怎么答得准、讲义怎么出得来。第四小节是图谱的算法。

4.1 资料入库：从文件到可检索的切片

切片参数：目标 240 token、上限 320、重叠 32。重叠是为了避免一句话被切断后两边都读不懂；结构感知切片优先在标题与段落边界切，而不是按字数硬切。

三步上传：init 返回 uploadId 与已上传分片 → 前端并发传分片 → complete 合并落 MinIO 并写 documents 记录。

事务提交后发事件：文件落库成功才触发入库，避免「文件还没传完，后台已经去解析」。

CAS 抢占执行权：后台用条件更新把状态从 UPLOADED 改成 PROCESSING，影响行数为 0 就放弃——重复事件不会重复处理。

解析 → 清洗 → 切片 → 向量化，向量写 PG、切片原文写 ES 与 MySQL，三者用 chunk_id 对齐。

收尾：成功置 READY，失败置 FAILED 并记录原因；另有定时任务回收长时间卡在 PROCESSING 的僵尸任务。

-- 抢执行权：只有第一个把状态从 UPLOADED 改走的人能处理
UPDATE documents SET status = 'PROCESSING'
 WHERE id = #{id} AND status = 'UPLOADED';

4.2 混合检索问答：两条通道，一次融合

为什么必须融合：向量通道能把「怎么提高召回」匹配到「召回率优化」，但面对课程编号、公式名容易糊；关键词通道正好相反。 两路取并集后用 RRF 按名次加权（不看原始分数，只看得第几名），避免两个通道分数量纲不同带来的偏差。

查询规划先判类型：问题够清楚就直接检索；口语化就改写；多重问题就拆成最多 3 条子查询分别检索后合并；「这个组一共有几份资料」这类全局问题走全量遍历，不走向量检索。

两路并行取 50：向量通道按余弦相似度取近邻，关键词通道按 BM25 打分取前列。

RRF 融合：每个候选的分数是它在各通道名次的倒数之和，同时被两路命中的切片自然排到最前。

聚类 + 邻窗扩展：相邻切片归为一簇，再向前后各扩一片，避免证据被切断成半句话。

证据分级：双通道互证或高分多命中 → 充分；仅单通道或命中数少 → 部分 / 弱；空 → 无，直接拒答。

// RRF：只看得第几名，不看原始分数
score(d) = Σ通道 i 1 / (k + ranki(d))      // 实现里 k = 0，归一化后落到 0~1

4.3 复习讲义：map / reduce 两阶段

三个刻意的取舍：① 不让模型直接排版——模型只写受控 Markdown，结构由 Java 拼，避免转义错误整份报废； ② 全程溯源——map 阶段就要求标来源，reduce 阶段禁止加料； ③ 异步 + 轮询——生成要几分钟，接口立刻返回 PENDING，前端 3 秒查一次状态。

4.4 知识图谱：从知识点到可执行的学习顺序

节点左边的圆点是掌握度：● 已掌握（正确率 ≥ 85%）、 ● 一般（≥ 60%）、● 薄弱（< 60%）、 ● 未检测。阶段内按「薄弱 → 未检测 → 一般 → 已掌握」排序，所以每个阶段最前面就是最该补的。

抽取：每份资料取前 30 个切片（上限 1 万字符），LLM 抽知识点与三类关系——先修（学 A 才能学 B）、组成（A 是 B 的一部分）、相关。每条关系必须附原文依据，防止模型凭空连线。

归一：概念名转成 node_key（小写、去空格标点），多份资料命中同一个概念就合并释义、取更高重要度、累加来源。

原子替换：单事务内先删旧边再删旧点再写新图，避免中途失败留下半张图。

分层：以先修边做 Kahn 拓扑排序，每轮取出「前置全部满足」的节点作为同一阶段；组成边反向视为弱前置（先整体后局部），这样即使模型只抽到层级结构，路径也不会退化成一个阶段。

断环与兜底：有环时取入度最小的节点强行解锁并标记 cycleDetected；完全孤立的知识点归入末尾「独立知识点」阶段，保证任何图都能出路径。

05

权限：三道关口，不依赖前端藏按钮

「统一管理」的前提是数据不能乱串。所有越权判断都在 Service 层，前端只负责不显示用不了的入口，不作为安全边界。

GATE 01

系统角色不进业务区

requireBusinessUser() 把 ADMIN 挡在小组、资料、问答之外。管理员没有业务数据的天然访问权——避免「运维账号能看所有学生资料」。

GATE 02

读权限统一入口

requireGroupReadable(groupId) 校验当前用户是该组成员（OWNER 或 MEMBER）。资料、问答、练习、讲义、图谱全部走这一个方法。

GATE 03

写权限单独收口

requireGroupOwner(groupId) 只给群主，用于改名、邀请审批、移除成员、删除他人资料等跨成员操作。

身份小组管理资料 / 问答 / 练习 / 图谱运营后台
ADMIN（系统管理员）✕ 不进业务区✕✓ 用户与 ETL 统计
OWNER（群主）✓✓✕
MEMBER（组员）✕✓✕

资源伪造（不存在的 ID、别人的文档 ID）统一返回「不存在或已删除」，不泄漏资源是否存在——这让攻击者无法通过错误信息探测他人的数据。

08

几个关键取舍

这部分是项目里真正做过判断的地方，也是最容易被追问的点。

01四套存储 vs 一套数据库

多一套存储就多一份运维成本，但换来了向量检索与中文分词的真实能力。做法是把复杂度收在 engine 适配层之后，业务侧只依赖接口，将来换向量库不动业务代码。

02混合检索 vs 只用向量

只用向量在「第 3 章那个公式」这类问题上会失手；只用关键词在「换个说法问同一件事」时召回很差。两路都跑再融合，代价是延迟增加约 100ms，换来命中率与鲁棒性。

03宁可拒答 vs 尽量回答

学习场景里，编造的答案比没有答案更糟——学生会背错。所以证据不足时直接返回「资料中未找到」，并把四级证据等级显式告诉用户，而不是让模型硬编一段。

04结构由代码拼 vs 让模型排版

早期试过让模型直接输出 LaTeX/HTML，一个转义符号错了整份产物就废。现在模型只产受控 Markdown，标题、元信息、章节顺序由 Java 拼装，稳定性换了一点点灵活性，值得。
